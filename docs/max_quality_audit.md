# Maximum-quality audit: processed data and analytical marts

## Decision

The current branch is a strong prototype, but it must not be presented as the final first project artifact until the items below are resolved and the full 37M-row build passes all gates.

The target is not the largest possible number of tables. The target is a defensible analytical data product with correct grain, explicit limitations, reproducible builds, BI-ready outputs, and no misleading conversion claims.

## Critical findings

### 1. Non-deterministic interaction identifier

`source_row_id` is currently generated by `ROW_NUMBER() OVER ()` while insertion-order preservation is disabled. An identifier derived from it is not guaranteed to remain stable between builds.

Required correction:

- replace the claimed unique business key with a deterministic row fingerprint based on source values;
- retain a separate technical scan ordinal only as non-business metadata;
- profile exact duplicate fingerprints instead of pretending identical source rows can be uniquely identified.

### 2. `cnt` must not be silently imputed into a canonical event count

The source definition describes `cnt` as the number of similar events in the context of the same user session. It is useful, but it is not an observed booking count and it is not a universal row weight.

Required correction:

- preserve raw `cnt`;
- expose `similar_event_count` only for valid positive values;
- expose a validity flag and missing/invalid coverage;
- calculate row-based and `cnt`-weighted measures separately;
- never label `SUM(cnt)` on booking rows as the number of bookings.

### 3. Search contexts are proxies, not sessions

The source has no explicit session ID or search-request ID. Grouping exact timestamps and request parameters is a deterministic proxy, but it can both merge different searches and split one real session.

Required correction:

- use `proxy_search_context` terminology everywhere;
- publish row-level booking interaction share as the primary directly observed outcome metric;
- publish booking-bearing proxy-context share as a secondary sensitivity metric;
- include ambiguity diagnostics: number of rows, clusters, markets and booking rows per proxy context;
- prohibit wording that presents proxy-context rate as checkout conversion.

### 4. Distance is hotel-specific and cannot be selected with `ANY_VALUE` at request grain

`orig_destination_distance` is the physical distance between the customer and a hotel. A proxy context may contain multiple hotel rows, so one arbitrary distance segment is not a valid request-level attribute.

Required correction:

- retain distance only at interaction grain;
- at proxy-context grain calculate min, median, max, missing share and booked-hotel distance where available;
- never use `ANY_VALUE(distance_segment)` for context segmentation.

### 5. Existing cohort mart is not a retention mart

The current cohort table has active users by cohort and month but lacks cohort size and retention rate.

Required correction:

- calculate fixed cohort size;
- calculate active-user retention;
- calculate booking-user share separately;
- flag right-censored cohort ages;
- avoid calling first observation registration or acquisition.

### 6. Destination opportunity logic is unstable for small samples

Ranking raw booking-context rates gives tiny destinations excessive influence. A fixed threshold of 100 rows is arbitrary.

Required correction:

- store numerator and denominator;
- calculate Wilson confidence intervals or another documented uncertainty estimate;
- compare destinations against a weighted global benchmark;
- calculate opportunity only for sufficiently supported destinations;
- expose expected incremental booking-bearing contexts as a scenario, not a causal forecast.

### 7. The Parquet output set is not atomic

Individual marts are replaced during the build before all downstream tables and quality checks pass. A failed run can leave a mixed set of old and new files.

Required correction:

- write every build to an immutable `data/marts/<build_id>/` directory;
- validate the complete build;
- update `LATEST_BUILD.json` only after all gates pass;
- keep the previous successful build as rollback.

### 8. Test coverage is structural, not end-to-end

The current tests validate specifications but do not execute all SQL against a controlled dataset.

Required correction:

- add a synthetic end-to-end fixture containing duplicates, nulls, invalid dates, clicks, bookings, multiple hotel rows per request and missing IDs;
- execute every fact, dimension and mart in CI;
- assert grains, reconciliations, rates and edge-case semantics.

## Maximum target architecture

### Source and staging

- `raw.train_events` — read-only prepared source view;
- `raw.destinations` — read-only destination latent-feature view;
- `stg_hotel_interactions` — typed, normalized, semantically named staging layer;
- `meta_source_profile` — row counts, date coverage, nulls, cardinality, ranges and source fingerprints.

### Core facts

- `fct_hotel_interactions` — one physical source row, all directly observed measures;
- `fct_proxy_search_contexts` — one deterministic request-like proxy with ambiguity diagnostics;
- `fct_user_day` — one user × event day, a robust grain not dependent on session reconstruction.

### Dimensions

- `dim_date` — continuous date spine spanning event, check-in and checkout dates;
- `dim_destination` — one destination with d1–d149 and observed geography coverage;
- `dim_user_first_seen` — first observed activity only;
- `dim_segment_definition` — ordered, documented segment values for BI sorting.

### Dashboard and analysis marts

- product daily and monthly health;
- directly observed interaction outcome daily/monthly;
- proxy-context outcome daily/monthly as sensitivity analysis;
- segment daily/monthly long-format marts;
- channel/site performance;
- destination performance and monthly dynamics;
- hotel-market performance;
- origin-to-destination route performance;
- check-in seasonality and booking-window behavior;
- travel-party and stay-pattern performance;
- user activity profile;
- cohort retention with cohort sizes and censoring;
- hotel-cluster descriptive performance;
- data-quality summary, daily monitoring and column profile.

## Required metric families

Every rate mart must preserve additive components so BI never averages percentages incorrectly.

1. `interaction_rows`
2. `click_rows`
3. `booking_rows`
4. `booking_interaction_share = booking_rows / interaction_rows`
5. `valid_similar_event_count`
6. `weighted_click_events`
7. `weighted_booking_events`
8. `weighted_booking_event_share`
9. `proxy_search_contexts`
10. `booking_bearing_proxy_contexts`
11. `booking_bearing_proxy_context_share`
12. `active_users`
13. `booking_users`
14. `booking_user_share`

None of these may be called revenue, purchase conversion, checkout conversion, CTR or causal uplift.

## Build metadata required for reproducibility

- build ID and UTC timestamps;
- Git commit and branch;
- Python and DuckDB versions;
- operating system;
- thread and memory settings;
- source paths, sizes, modification times, row counts and schema;
- SHA-256 for SQL files and small configuration files;
- row count, grain-key uniqueness, date range and Parquet size per object;
- complete quality-gate report;
- immutable build directory and rollback pointer.

## Quality gates

The final build must include at least the following gate groups:

- source-to-fact row reconciliation;
- valid domain checks;
- exact grain-key uniqueness for every dimension and mart;
- date-spine continuity;
- daily-to-monthly reconciliation;
- segment totals reconcile independently for every segment type;
- destination and market totals reconcile to eligible populations;
- all rate numerators are between zero and denominators;
- all published rates are in [0, 1];
- no required mart is empty;
- no output file belongs to a failed build;
- duplicate and null coverage are explicitly reported;
- proxy-context ambiguity rates are reported;
- cohort retention at age zero equals one for eligible identified users;
- output schema snapshot matches the documented contract.

## Final deliverables for project item 1

1. Versioned DuckDB database.
2. Versioned Parquet facts, dimensions and marts.
3. Data model diagram and dependency graph.
4. Complete table and column data dictionary.
5. Metric dictionary with allowed and prohibited interpretations.
6. Source profiling report.
7. Build manifest and validation report.
8. Reproducible one-command build.
9. Synthetic end-to-end integration tests.
10. A compact README section showing how the future dashboard consumes each mart.

## Acceptance rule

The artifact is complete only after a full local run on all source rows, successful quality gates, manual inspection of representative records, and a documented reconciliation table. Passing Ruff and unit tests alone is insufficient.
